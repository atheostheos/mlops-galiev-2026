# Регламент статуса модели

## 1. При каких условиях модель переводится в Staging

Модель переводится в `Staging` при выполнении всех условий ниже:
1. модель обучена на версии проекта с закоммиченным состоянием на `main`
  (`git_sha` в тегах прогона совпадает с коммитом в `main`)
2. данные взяты из версии под DVC (есть `data_md5`, совпадающей с одной из версий в DVC)
3. CI на этом коммите зелёный: пайплайн вопроизводится
4. ROC-AUC на валидации не ниже определенного на данный момент quality гейта
5. модель зарегистрирована с `input_example`, у неё есть явно определенная сигнатура

## 2. Какие проверки проходят перед Production

Кандидат из `Staging` переходит в продакшн при выполнении всех условиях ниже:
1. ROC-AUC кандидата статистически значимо выше метрики текущей продакшн модели
2. Аналогично проверки перед `Staging` зеленый CI на текущей версии проекта
3. Сигнатура модели совпадает с настройкой сигнатуры на продакшене. Иначе проверка на соответсвие сигнатуры не пройдет и модель не запустится на проде
4. Помимо метрики смотрим на скорость инференса и требовательность к ресурсам. В зависмости от задачи более точная модель, но ниже минимально требуемой скорости инференса, не подходит для продакшн версии

## 3. Кто принимает решение

- Перевод в `Staging` — автор изменения
- Перевод в `Production` — владелец модели после проверки на соответсвие требованиям. Решение с объяснением причины перевода фиксируется в описании модели в MLflow

## 4. Как выполняется откат

Откат выполняется в данных случаях:
- метрики в проде деградировали
- обнаружена ошибка в модели (часть продовых экземпляров неккоректно обрабатываются моделью)

Причина в дерградации метрик или ошибки модели могут быть связаны не с конкретной версией модели. Проблема может быть в самом пайплайне или инференсе: неккорректная предобработка данных, неккоректная отработка кода на крайних значениях и т.п.
Перед откатом требуется найти причину и только в случае проблемы самой модели производить откат.

Для отката необходимо передать алиас `@champion` прошлой продакшн модели ч-з веб-интерфейс MLFlow


## Почему при автоматическом промоуте по метрике используется минимальный порог

Незначительное улучшение метрик новой версии модели может быть связано скорее с шумом, чем реальным улучшением качества самой модели. Поэтому при промоуте за счет порога гарантируется проверка значимого улучшения, чтобы не менять модель каждый раз при незначительном улучшении.
